# Handshake Authentication

Handshake authentication signs your user into Lucra using a token **your** backend signs — no Lucra
phone entry screen. Your app registers a token provider once; from then on Lucra resolves a session
automatically whenever one is needed.

Phone authentication remains the fallback: if no provider is registered, or a handshake attempt
fails, users can still sign in with their phone number. The one exception is `tosNotAccepted` — a
new user who hasn't accepted the Terms of Service is resolved by the `HANDSHAKE_TOS` flow, not by
phone auth. See [Terms of Service](#terms-of-service).

> Handshake auth requires Lucra-side provisioning (a shared signing key and a token exchange profile
> for your tenant). Contact Lucra before integrating.

## The token contract

Your backend signs the token with the shared key Lucra issues you.

* **Algorithm:** `HS256`
* **Payload:**

```json
{
  "sub": "your-stable-user-id",
  "phone_number": "+15555550100",
  "email": "user@example.com",
  "iat": 1735689600,
  "jti": "b9d1f0e6-2f0b-4a3e-9b06-8a9e5b0f3f4c"
}
```

| Claim | Required | Notes |
|---|---|---|
| `sub` | Yes | Your stable identifier for the user. |
| `phone_number` | Yes | E.164. Lucra resolves the account by this — a match signs into the existing Lucra user, a new number creates one. |
| `email` | No | Populates the Lucra profile when present. |
| `iat` | Yes | Issued-at, in seconds. Tokens are accepted for 60s (30s clock tolerance), so mint per request rather than caching. |
| `jti` | Yes | Unique per token; the handle for replay protection. |

Send nothing else — no `iss`, `aud` or `exp`. An unexpected claim can only reject a token that would
otherwise pass.

### Keep the signing key out of the app

**The signing key must never ship in your JavaScript bundle.** A bundle is trivially extractable from
a shipped app, and anyone holding the key can mint a token for any of your users. The provider is a
callback precisely so the app can fetch an *already-signed* token from your authenticated API over
TLS, using the session the user already has.

Two related points worth knowing:

* The token crosses the React Native bridge in plaintext, so it is visible to anything inspecting
  bridge traffic (`MessageQueue.spy`, dev-menu bridge inspectors). Never log it. Short-lived,
  single-use tokens bound the exposure — which the 60s validity already enforces.
* Messages thrown by your provider are surfaced through Lucra's logging as `providerFailed`, so keep
  user identifiers and tokens out of them.

## Step 1 — Register the provider

```ts
import { LucraSDK } from '@lucra-sports/lucra-react-native-sdk';

await LucraSDK.init({ apiKey, environment });

await LucraSDK.registerHandshakeAuthTokenProvider(async () => {
  // Your session, your backend. Lucra never sees your credentials.
  const response = await fetch('https://api.example.com/lucra-token', {
    headers: { Authorization: `Bearer ${mySessionToken}` },
  });
  const { token } = await response.json();
  return token;
});
```

Registering only stores the function: it signs nobody in, has no auth side effects, and is safe to
call more than once. Pass `null` to clear it, which puts Lucra flows back on phone auth.

Calling it before `LucraSDK.init(…)` resolves is safe — the registration is applied as soon as
initialization completes. Register as early as you can, so a session can be resolved before any
Lucra UI appears.

Your function must return within **5 seconds** or the attempt fails with `providerTimedOut`.

> On an Android emulator, `localhost` is the emulator itself — use `10.0.2.2` to reach your host
> machine.

## Step 2 — Sign in

```ts
try {
  const user = await LucraSDK.signInWithHandshakeAuth();
  console.log('Signed in as', user.username);
} catch (e) {
  const error = e as LucraHandshakeAuthError;
  if (error.code === 'tosNotAccepted') {
    // See "Terms of Service" — do NOT fall back to phone auth here.
    await LucraSDK.present({ name: LucraSDK.FLOW.HANDSHAKE_TOS });
  } else {
    // Everything else: phone auth still works.
    await LucraSDK.present({ name: LucraSDK.FLOW.ONBOARDING });
  }
}
```

The promise resolves once the user **profile** has loaded, not merely once the tokens land, so the
returned user is immediately usable. Concurrent calls share a single in-flight exchange.

### An existing session wins

Calling this while a user is already signed in reports that user and runs no exchange. The same
holds while a stored session is still being restored — the usual state a launch-time call arrives in
— so it is safe to call unconditionally on every app start.

To sign a **different** user in, sign the current one out first:

```ts
await LucraSDK.logout();
await LucraSDK.signInWithHandshakeAuth();
```

### Or let the SDK do it

If you only register a provider, the SDK signs the user in on its own wherever it would otherwise
have shown the login screen:

* **Presenting an auth-gated flow** while signed out runs the handshake first, behind a loading
  state — the phone entry screen never appears while the exchange runs.
* **Tapping auth-gated content mid-flow** (joining a tournament, say) completes the handshake inline
  and then proceeds.
* **An expired or revoked session** is recovered silently on the next request.
* **Tapping a signed-out [Lucra component](1.2.8_lucracomponents.md)** runs the handshake in place
  instead of presenting Lucra's login inside your screen. Components sit in your own view hierarchy,
  so the SDK shows no loading UI of its own there — observe `isHandshakeAuthInFlight` if you want a
  spinner.

All of these fall back to phone auth if the handshake fails, with the one exception below.

## Terms of Service

A user who is **new to Lucra** has no account yet, and Lucra will not create one until they agree to
its Terms of Service. Their first exchange is refused with `tosNotAccepted`. Users who already have
a Lucra account are never affected.

This is the one failure that is **not** a cue to fall back to phone auth — phone auth cannot create
the account either. Treating it as a generic failure dead-ends exactly the users you are trying to
onboard.

**When Lucra is presenting the flow**, there is nothing to do: the terms step is shown inline, and
once the user agrees the sign-in resumes and continues into the flow they asked for.

**When you called `signInWithHandshakeAuth` yourself**, present `LucraSDK.FLOW.HANDSHAKE_TOS` off
that specific error. It needs no session, captures the agreement, resubmits the sign-in with a fresh
token from your provider, and dismisses once the user is signed in.

Because the SDK resubmits the exchange itself, your original `signInWithHandshakeAuth` promise has
already rejected — watch the `user` listener (or call `getUser()`) to learn the sign-in succeeded:

```ts
LucraSDK.addListener('user', (user) => {
  if (user) {
    // Signed in, possibly via the HANDSHAKE_TOS flow.
  }
});
```

Present `HANDSHAKE_TOS` **only** in response to that error. It is not an entry point.

### Skipping the step

If your own onboarding already captures agreement to Lucra's terms:

```ts
await LucraSDK.registerHandshakeAuthTokenProvider(provider, {
  bypassTosAgreement: true,
});
```

The bypass is honored only for tenants Lucra has permitted. Otherwise the request is ignored, new
users see the terms step as they would have, and a log records that it was asked for and not granted
— so a build that silently loses the bypass behaves correctly rather than failing. **Talk to Lucra
before setting it**; it carries a legal obligation you are taking on.

## Observing state

Handshake failures fall back to phone auth silently, which makes a broken integration look like a
signed-out user. `subscribeToAuthState` is how you tell the two apart.

```ts
const unsubscribe = LucraSDK.subscribeToAuthState((state) => {
  console.log(state.isHandshakeAuthInFlight); // true while an exchange runs
  console.log(state.handshakeAuthError);      // the LAST failure, or null
  console.log(state.isResolvingAuthState);    // iOS only; null on Android
});

// Later
unsubscribe();
```

`onChange` fires immediately with the last known state and again on every change. Any number of
subscribers can be active at once. There is also a hook:

```ts
import { useAuthState } from '@lucra-sports/lucra-react-native-sdk';

function SignInButton() {
  const { isHandshakeAuthInFlight } = useAuthState();
  return <Button disabled={isHandshakeAuthInFlight} title="Play" onPress={play} />;
}
```

and a one-shot read, `await LucraSDK.getAuthState()`.

Three things to know about the payload:

* **`handshakeAuthError` is the last failure, not a current one.** It is cleared when the next
  exchange starts. Don't read a non-`null` value as "something is failing right now".
* **`isResolvingAuthState` is iOS only** and is `null` on Android, whose SDK exposes no equivalent.
  A falsy check therefore does the right thing on both platforms without a `Platform.OS` branch.
  It starts `true` and can flip back to `true` mid-session during a sign-in, so subscribe rather
  than reading it once.
* All three values arrive in **one** payload, so you can never observe `isHandshakeAuthInFlight`
  going false before the error that caused it.

## Error reference

Rejections from `signInWithHandshakeAuth` — and the `handshakeAuthError.code` above — use these
codes. Every one carries a `message`, and most carry a `recoverySuggestion` naming what to check.

| Code | Meaning | What to check |
|---|---|---|
| `noProviderRegistered` | `signInWithHandshakeAuth` was called with no provider | Call `registerHandshakeAuthTokenProvider` first |
| `providerTimedOut` | Your function did not return within 5s | Your token endpoint's reachability from the device |
| `providerFailed` | Your function rejected | The `message` — it carries your own error's text |
| `exchangeFailed` | Lucra rejected the token | Signature (is the key the one Lucra issued, encoded the same way?), `iat` freshness, and the payload shape above |
| `tosNotAccepted` | The user is new to Lucra and has not accepted the Terms of Service | Nothing — this is not a fault. Present `HANDSHAKE_TOS`, not phone auth |
| `tenantIdUnavailable` | Initialization never produced a tenant | That `LucraSDK.init` resolved with a valid API key |
| `profileTimedOut` | **Android only.** The session landed but the profile did not | Connectivity; retry — the credentials are already installed |
| `notInitialized` | `LucraSDK.init()` has not resolved yet | Await `init` before calling. *Android may report this as `unknownError` instead; its SDK swallows the underlying error.* |
| `unknownError` | Unclassified, or a concurrent sign-out superseded the attempt | Retry if the sign-in is still wanted |

## Sign-out

`LucraSDK.logout()` ends the Lucra session and stops the SDK from silently re-authenticating on a
token refresh. It does **not** unregister your provider: the next time you present a Lucra flow that
needs a session, the SDK runs the handshake again and signs the same user back in — usually what you
want, since they are still signed into your app.

To keep a user signed out of Lucra, clear the provider as part of your own sign-out:

```ts
await LucraSDK.registerHandshakeAuthTokenProvider(null);
await LucraSDK.logout();
```
