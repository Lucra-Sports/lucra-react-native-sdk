# Handshake Authentication

Handshake auth signs a user into Lucra using **your** existing session, with no Lucra login UI. Instead of asking a user who is already signed into your app to verify a phone number again, your app hands Lucra a short-lived, partner-signed token; Lucra exchanges it for a Lucra session behind the scenes.

It is purely additive. Phone auth still exists and remains the fallback: with no provider registered, or when an exchange fails, the SDK presents its phone auth screen exactly as before. The one exception is `tosNotAccepted` — a user new to Lucra who has not accepted the Terms of Service is resolved by the `HANDSHAKE_TOS` flow, not by phone auth. See [Terms of Service](#terms-of-service).

> Handshake auth requires Lucra-side provisioning (a shared signing key and a token exchange profile for your tenant). Contact Lucra before integrating.

## How it works

1. You register a **token provider** — an async function returning a partner-signed JWT that identifies your current user.
2. Lucra calls that provider (with a 5 second timeout) and exchanges the token for a Lucra session.
3. The user lands in the same Lucra account they would have reached via phone auth, matched on the phone number in the token.

Your session never leaves your app: the provider calls **your** backend with **your** credentials, and Lucra only ever sees the token it returns.

## The token contract

Your backend signs the token with the shared key Lucra issues you. The key must never ship in the app — the provider exists so the app can fetch an already-signed token from your authenticated API.

* **Algorithm:** `HS256`
* **Payload:**

```json
{
  "sub": "your-stable-user-id",
  "phone_number": "+15555550100",
  "email": "user@example.com",
  "iat": 1735689600,
  "jti": "b9d1f0e6-2f0b-4a3e-9b06-8a9e5b0f3f4c"
}
```

| Claim | Required | Notes |
|---|---|---|
| `sub` | Yes | Your stable identifier for the user. |
| `phone_number` | Yes | E.164. This is what Lucra resolves the account by — a match signs into the existing Lucra user, a new number creates one. |
| `email` | No | Populates the Lucra profile when present. |
| `iat` | Yes | Issued-at, in seconds. Tokens are accepted for 60s (30s clock tolerance), so mint per request rather than caching. |
| `jti` | Yes | Unique per token; the handle for replay protection. |

Send nothing else — no `iss`, `aud`, or `exp`. An unexpected claim can only reject a token that would otherwise pass.

## Step 1 — Register the provider

Register once, any time after `LucraSDK.init` resolves. Registering only stores the function: it signs nobody in, has no auth side effects, and is safe to call repeatedly.

```ts
import { LucraSDK } from '@lucra-sports/lucra-react-native-sdk';

LucraSDK.registerHandshakeAuthTokenProvider(async () => {
  // Use YOUR session against YOUR backend.
  return await MyBackend.fetchLucraHandshakeToken();
});

// Pass null to clear it — Lucra flows go back to phone auth.
LucraSDK.registerHandshakeAuthTokenProvider(null);
```

The provider must resolve within **5 seconds** or the attempt fails with `providerTimedOut`. The token is single use, so Lucra calls the provider again every time it needs one; do not cache a token and return it twice.

## Step 2 — Sign in

Registering does not sign anyone in; you choose the moment.

```ts
try {
  const user = await LucraSDK.signInWithHandshakeAuth();
  console.log('Signed in as', user?.username);
} catch (error) {
  // Do not dead-end the user — phone auth still works.
  const e = error as LucraHandshakeAuthError;
  console.warn(`${e.code}: ${e.message} — ${e.recoverySuggestion}`);
}
```

It resolves once the user **profile** has loaded, not merely once the tokens land, so the returned `LucraUser` is immediately usable. Concurrent calls share a single in-flight exchange.

### An existing session wins

Calling this while a user is already signed in reports that user and runs no exchange. The same holds while a stored session is still being restored — the usual state a launch-time call arrives in — so it is safe to call unconditionally on every app start.

To sign a **different** user in, log the current one out first:

```ts
await LucraSDK.logout();
await LucraSDK.signInWithHandshakeAuth();
```

### Or let the SDK do it

If you only register a provider, the SDK signs the user in wherever it would otherwise have shown its login screen:

* **Presenting an auth-gated flow** while signed out runs the handshake first, holding a loading state instead of the phone auth screen.
* **Actions that need a session** — joining a tournament, for example — complete the handshake inline and then proceed.
* **An expired or revoked session** is recovered silently on the next request.
* **Tapping a signed-out [Lucra component](1.2.8_lucracomponents.md)** runs the handshake in place instead of presenting Lucra's login inside your screen.

All of these fall back to phone auth if the handshake fails, with the Terms of Service exception below.

## Terms of Service

A user who is **new to Lucra** has no account yet, and Lucra will not create one until they agree to its Terms of Service. Their first exchange is refused with `tosNotAccepted`. Users who already have a Lucra account are never affected.

This is the one failure that is **not** a cue to fall back to phone auth — phone auth cannot create the account either. Treating it as a generic failure dead-ends exactly the users you are trying to onboard.

**When Lucra is presenting the flow**, there is nothing to do: the acceptance step is shown inline, and once the user agrees the sign-in resumes and continues into the flow they asked for.

**When you called `signInWithHandshakeAuth` yourself**, present `LucraSDK.FLOW.HANDSHAKE_TOS` off that specific code. It needs no session, captures the agreement, resubmits the sign-in with a fresh token from your provider, and dismisses once the user is signed in.

```ts
try {
  await LucraSDK.signInWithHandshakeAuth();
} catch (error) {
  const e = error as LucraHandshakeAuthError;
  if (e.code === 'tosNotAccepted') {
    // New user, one agreement short of an account.
    await LucraSDK.present({ name: LucraSDK.FLOW.HANDSHAKE_TOS });
  } else {
    presentPhoneAuth();
  }
}
```

Present `HANDSHAKE_TOS` **only** in response to that code. It is not an entry point.

### Skipping the step

If your own onboarding already captures agreement to Lucra's terms, the step can be skipped:

```ts
LucraSDK.registerHandshakeAuthTokenProvider(
  async () => await MyBackend.fetchLucraHandshakeToken(),
  { bypassTosAgreement: true }
);
```

The bypass is honored only for tenants Lucra has permitted. Otherwise the request is ignored, new users see the acceptance step exactly as they would have, and a log records that it was asked for and not granted — so a build that silently loses the bypass still behaves correctly. **Talk to Lucra before setting it**; it carries a legal obligation you are taking on.

## Observing state

Handshake failures fall back to phone auth silently, which makes a broken integration look like a signed-out user. `addHandshakeAuthListener` is how you tell them apart. It takes both callbacks in one map and returns a single unsubscribe function, like [`addContestListener`](1.2.10_lucra_event_listener.md).

```ts
const unsubscribe = LucraSDK.addHandshakeAuthListener({
  onError: (error) => {
    // null when a new attempt clears the previous failure.
    if (error) {
      console.warn(`${error.code}: ${error.message} — ${error.recoverySuggestion}`);
    }
  },
  onInFlightChange: (inFlight) => {
    // True while an exchange runs; Lucra suppresses its own login UI for
    // the duration, so this is when to show your own loading state.
    setLoading(inFlight);
  },
});

// Call this when you no longer need the listeners (e.g., on unmount).
unsubscribe();
```

## Sign-out

`LucraSDK.logout()` ends the Lucra session and stops the SDK from silently re-authenticating on a token refresh. It does **not** unregister your provider: the next time you present a Lucra flow that needs a session, the SDK runs the handshake again and signs the same user back in — usually what you want, since they are still signed into your app.

To keep a user signed out of Lucra, clear the provider as part of your own sign-out:

```ts
LucraSDK.registerHandshakeAuthTokenProvider(null);
await LucraSDK.logout();
```

## Error reference

Rejections from `signInWithHandshakeAuth` are typed as `LucraHandshakeAuthError`, and the `onError` payload as `LucraHandshakeAuthFailure`. Both carry a `code`, a `message`, and a `recoverySuggestion` naming what to go look at.

| Code | Meaning | What to check |
|---|---|---|
| `noProviderRegistered` | `signInWithHandshakeAuth` ran with no provider | Call `registerHandshakeAuthTokenProvider` after `init` and before presenting a Lucra flow |
| `providerTimedOut` | Your provider did not resolve within 5s | Your token endpoint's reachability from the device |
| `providerFailed` | Your provider rejected | Its rejection reason; typically your own session expired or the endpoint errored |
| `exchangeFailed` | Lucra rejected the token | The signature, `iat` freshness, and the payload shape above |
| `tosNotAccepted` | The user is new to Lucra and has not accepted the Terms of Service | Nothing — this is not a fault. Present `FLOW.HANDSHAKE_TOS`, not phone auth |
| `tenantIdUnavailable` | Initialization never produced a tenant | That `LucraSDK.init` resolved with a valid API key |
| `profileTimedOut` | Android only: the session landed but the profile did not | Connectivity; retry the sign-in — the credentials are already installed |
| `unknownError` | Android only: a concurrent sign-out superseded the attempt, or it failed unexpectedly | Retry the sign-in if it is still wanted |

## Timeouts

| Wait | Limit | On expiry |
|---|---|---|
| A stored session still being restored | 5s | Proceeds with the exchange |
| Your token provider | 5s | `providerTimedOut` |
| SDK initialization (tenant resolution) | 15s | `tenantIdUnavailable` |
| A gated sign-in the user is waiting on | 10s | Falls back to phone auth |
| The user profile after a successful exchange | — | `profileTimedOut` (Android) |

## API reference

```ts
LucraSDK.registerHandshakeAuthTokenProvider(
  provider: (() => Promise<string>) | null,
  options?: { bypassTosAgreement?: boolean }
): void;

LucraSDK.signInWithHandshakeAuth(): Promise<LucraUser | null>;

LucraSDK.addHandshakeAuthListener(listeners: {
  onError?: (error: LucraHandshakeAuthFailure | null) => void;
  onInFlightChange?: (inFlight: boolean) => void;
}): () => void;
```

`signInWithHandshakeAuth` resolves `null` only if a session lands without a profile; on Android that case rejects with `profileTimedOut` instead.
